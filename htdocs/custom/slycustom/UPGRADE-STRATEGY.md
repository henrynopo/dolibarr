# 如何升级到 Dolibarr 最新版并便于日后持续升级

当前你处于 **SLY14.0**（基于官方 14.0 + 大量核心定制）。要「最方便」地升到**最新版**（如 22.0.x）且**日后升级省心**，核心思路是：**以官方代码为主、定制尽量收进模块和少量补丁**。

---

## 一、两种升级思路对比

| 思路 | 做法 | 升级到最新的难度 | 日后每次升级 | 适合情况 |
|------|------|------------------|--------------|----------|
| **A. 直接换官方最新 + 模块** | 全新装官方 22.0.x，只装 slycustom 模块，核心只打「最少必要」补丁 | 一次性工作大（要核对功能、补丁要适配 22.x） | 很省事：跟官方升级即可 | 能接受部分 SLY 功能用新版本方式实现或暂时不做 |
| **B. 在 14.0 上继续合并官方** | 继续用 SLY14.0，只合并官方 14.0 的修复 | 不能算「升到最新」（仍是 14.0） | 每次合并要解决大量冲突 | 必须留在 14.0、又要官方修复时 |

结论：**若目标真是「升级到最新版 + 日后好升级」**，应选 **A**，并把定制收敛到「模块 + 极少核心补丁」。

---

## 二、推荐做法：以官方为主 + 模块 + 最小补丁（便于日后升级）

### 2.1 原则

1. **主代码 = 官方 Dolibarr**（如 22.0 或当前最新分支），不长期维护一整份 SLY  fork。
2. **定制尽量放进 slycustom 模块**：PDF、ShipsGo 逻辑、导出入口、能在 hook 里实现的都进模块。
3. **核心只保留「不得不改」的补丁**，且单独成文件（如 `patches/` 下的 .patch），每次升级后只重新应用这几处。
4. **数据库**：按官方升级说明做（备份 → 用新版本文件 → 访问 install/upgrade.php 等）。

这样以后每次官方发版：**拉官方新版本 → 重新打同一批补丁（若有冲突就改补丁）→ 测一遍**，即可。

### 2.2 仓库与分支建议（若用 Git）

```text
你的仓库里建议保留两个 remote：
  origin   = 你的仓库（例如 henrynopo/dolibarr）
  upstream = 官方 https://github.com/Dolibarr/dolibarr

分支思路（二选一或混用）：

方案 1：每个大版本一条「定制分支」
  - upstream/22.0   → 只读，跟踪官方 22.0
  - sly-22.0        → 你在 22.0 上的定制：从 upstream/22.0 拉出来，只加 slycustom 模块 + 少量 patch
  将来官方 23.0 出来：
  - upstream/23.0
  - sly-23.0        → 从 upstream/23.0 拉出，把 slycustom 拷过去，再重新应用/适配同一批补丁

方案 2：单分支跟踪官方最新
  - main = 跟踪 upstream 的某个分支（如 22.0 或 main）
  - 你的定制 = main 上只有 slycustom 目录 + 若干 .patch，升级时：git pull upstream 22.0，再 git apply patches/*.patch
```

这样「升级到最新」= 换到官方最新分支并应用你的补丁；「日后升级」= 同分支 pull + 重新 apply 补丁。

### 2.3 第一次「升到最新」的具体步骤（示例：升到 22.0.x）

1. **备份**
   - 数据库完整备份。
   - 当前 SLY14.0 的 `htdocs/`（或整个安装目录）打 zip 备份。

2. **准备「干净」的官方最新**
   - 新目录或新分支：只放官方 22.0 代码（从 [Dolibarr GitHub](https://github.com/Dolibarr/dolibarr) 克隆或下载 22.0.x 发布包）。
   - 不要直接在你的 SLY14.0 上改，避免混入大量 14 的修改。

3. **把 slycustom 放进去**
   - 把当前 `htdocs/custom/slycustom` 整个拷贝到官方 22.0 的 `htdocs/custom/` 下。
   - 在 22.0 里检查模块是否被识别（首页 → 配置 → 模块/应用 → 外部模块）。若有 API 或类名变更，按报错微调模块代码。

4. **核对并精简「核心补丁」**
   - 你已有清单：`PATCHES-OFFICIAL-14.md`（最小 PDF+ShipsGo 补丁）、`CORE-CUSTOMIZATIONS-FULL-LIST.md`（全部修改）。
   - 在 22.0 上只保留**业务上必须**的补丁（例如 ShipsGo 在 expedition 的集成）。14.0 的补丁不能直接 apply 到 22.0，需要：
     - 用 `CORE-CUSTOMIZATIONS-FULL-LIST.md` 找到对应文件，
     - 在 22.0 的对应文件中**手工做同等逻辑**，或
     - 根据 14.0 的 diff 整理成针对 22.0 的新 .patch，再 `git apply` 测试。
   - 建议：第一次只做「PDF + ShipsGo + 一两项最关键业务」，其余以后用 hook 或接受 22.0 自带行为。

5. **数据库与配置**
   - 若从 14.0 数据升级：用官方 14→15→…→22 的升级说明或逐版 upgrade.php。
   - 若全新安装 22.0：新装后只导入必要数据或重新配置。
   - `conf/conf.php`、文档目录等按官方文档迁移。

6. **测试与上线**
   - 在测试环境完整走一遍：登录、订单、发票、发货、ShipsGo、PDF、导出等。
   - 确认无误再切生产。

### 2.4 日后每次升级（例如 22.0.4 → 22.0.5 或 22 → 23）

1. **拉官方新版本**
   - `git fetch upstream && git merge upstream/22.0`（或你跟踪的分支）。

2. **重新应用你的补丁**
   - `git apply patches/*.patch`；若有冲突，解决后 `git add` 并视情况用 `git add -p` 只提交你的定制部分。
   - 若你只有少量文件手工改，就重新做一遍相同的手工修改并和官方 diff 对比，避免漏改。

3. **检查 slycustom 模块**
   - 官方可能改 hook、类名、API；若有报错或行为变化，只改 slycustom，不改核心。

4. **跑升级脚本与测试**
   - 数据库：访问 install/upgrade.php（若官方有结构变更）。
   - 再跑一遍核心流程测试。

这样「升级到最新」和「日后升级」都围绕「官方 + 模块 + 最少补丁」一条线，最省事。

## 三、若暂时不能放弃 14.0：在 SLY14.0 上为「以后升级」做准备

若短期内必须留在 SLY14.0，仍建议为将来迁移做准备：

1. **继续用 slycustom 模块**
   - 把已抽进 slycustom 的 PDF、ShipsGo、导出保留在模块里；新需求尽量用模块或 hook 实现，少改核心。

2. **核心改动做成 patch 保留**
   - 在 SLY14.0 上执行：
     - `git diff upstream/14.0 -- htdocs/expedition/card.php htdocs/expedition/list.php ... > patches/shipsgo-14.patch`
     - 只选**必须**的文件，生成少量 .patch 文件，放到 `patches/` 或单独仓库，并写清「打在哪些路径、用于 14.0」。
   - 以后迁到 22.0 时，这些 patch 不能直接 apply，但可作「逻辑清单」：在 22.0 上对着清单逐项实现或重做 patch。

3. **定期合并官方 14.0**
   - `git fetch upstream && git merge upstream/14.0`，解决冲突时以「保留 SLY 业务逻辑」为准，必要时用 `git log upstream/14.0 -- 文件` 看官方改了什么再合。

这样当前仍用 14.0，但定制更集中，将来切到 22.0 时迁移路径更清晰。

---

## 四、小结表

| 目标 | 建议做法 |
|------|----------|
| **马上用上最新版（如 22.0.x）且日后升级简单** | 新装官方 22.0 → 放入 slycustom → 只打最少必要核心补丁（并整理成 .patch）→ 以后升级：拉官方 + 重打补丁 + 测 |
| **暂时不能离开 14.0** | 继续 SLY14.0，但新定制尽量进 slycustom；把现有核心改动整理成少量 .patch；定期 merge upstream/14.0；为将来迁 22.0 做准备 |
| **长期最少维护成本** | 以官方为主 + 定制只在 slycustom + 核心补丁控制在极少数文件并文档化，每次大版本升级时只「重打同一批补丁」并做一次回归测试 |

按上面做，**升级到最新版**和**日后持续升级**都会最方便。
